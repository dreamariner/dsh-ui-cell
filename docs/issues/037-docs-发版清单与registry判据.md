# 037 · docs · 发版清单 + 发布判据

## 背景

0.6.0 发版那天踩了一个坑：**npm 的 token 失效了，publish 日志里是 `PUT 401`**，
网页登录重新认证后 npm 自己重试拿到 `202` 并把包发了出去。但 npm **在 401 之后
仍然 `exit 0`**：当时的判断差点误成「第一次就成功了」。更要紧的是：如果那次
网页登录没补上，npm 大概率还是 `exit 0`，**「退出码为 0」就等于「发成功了」**
这个判据从根上就是错的。

结论当时说清楚了（写进对话里），但**没落在仓里**。下次发版还会再绕一圈。
本 issue 把这条判据连同整套发版流程写进仓。

## 写进仓的东西

### 1. `docs/wiki/05-DSH升级SOP.md` 新增「一之四 · 发布到 npm（发版清单）」

九节内容：

| 小节 | 内容 |
|---|---|
| 前置检查 | 9 项检查表（工作树干净 / 已推送 / 护栏全绿 / 上游保真 / 用法速查无漂移 / token 清单 / CI 绿 / 版本没发过 / 打包清单），每项给命令与期望 |
| 发布 | `pnpm publish` + `git tag` 命令；tag **无 `v` 前缀**（跟仓库既有约定） |
| **发布成功的判据** | **看 registry，不看 npm 退出码**；给出 401 → 网页登录 → 202 的真实日志形态与 `npm view` 判据 |
| 传播要多久 | 分三层（registry 元数据 1–5 分钟 / CDN 边缘 / 本地 `_cacache`），实测约 3 分钟；查不到时先分清是缓存还是传播 |
| 发布后必做 | 从 registry **真装一次**：`npm i -D` → 看版本 → CLI 可用 → `add` 能跑 → 消费端 `tsc --noEmit` 过 |
| 最后两笔 | 父仓 submodule 指针、文档站（生成物，改了要重建再推） |

### 2. 顶部「零、先记住这三条」改成四条

第 4 条即「发布成功看 registry，不看 npm 退出码」：放在最前面是因为它是
**唯一一条不读就会误判成功**的。

### 3. 「五、别做的事」加两条

- ❌ 拿 npm 的退出码当发布成功的证据（401 之后它照样 `exit 0`）
- ❌ 本机绿就当发出去的包是好的（`.gitignore` 那个坑：本机一直绿、克隆下来是坏的）

### 4. `AGENTS.md` 新红线 11

红线是「破坏即返工」的清单，这条属于「照做就会误判」的一类，故入红线：

> **发布成功看 registry，不看 npm 退出码**：判据只有一条：
> `npm view @dreamariner/dsh-ui-cell versions` 里有没有当前版本。发布后还要从 registry 真装一次。

### 5. `docs/wiki/README.md` 的索引与目录树补「发版清单」

## 顺带记一笔

写这节时踩到了另一个坑：**heredoc 里打中文会被 shell/python 吃掉字节**
（写出来是 U+FFFD 替换符）。第一次替换没匹配上（因为源串本身就是坏的），
第二次用 `chr(0xFFFD)` 定位才清干净。教训：**含中文的批量文本改写走脚本文件，
不走 shell heredoc**。

另外补了一条实测：**`pnpm publish` 默认带 git 检查，工作树脏直接拒绝**
（`ERR_PNPM_GIT_UNCLEAN`），`--dry-run` 同样被拦。所以「工作树干净」不是软规矩，
是 pnpm 的硬门槛，先提交再发，别用 `--no-git-checks` 绕过。
